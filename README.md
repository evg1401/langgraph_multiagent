# Контент-фабрика на LangGraph

Мультиагентный конвейер: **стратег -> копирайтер -> редактор -> паблишер**,
с петлёй доработки между копирайтером и редактором (лимит кругов — 3,
`app.config.DEFAULT_MAX_REVISIONS`).

Проверялось на Python 3.12.

## Запуск

```bash
pip install -r requirements.txt
cp .env.example .env
python main.py
```

У приложения нет параметров командной строки — вся настройка через `.env`.

Описание цикла работы приложения: после запуска агентов приложение ожидает их ответа и завершает свою работу.

## Переменные окружения

Обязательные — запасных значений в коде нет, при отсутствии любой из них
запуск прерывается с перечнем недостающих имён:

| Переменная | Назначение |
| --- | --- |
| `LLM_API_KEY` | ключ доступа к API модели |
| `LLM_BASE_URL` | адрес OpenAI-совместимого API |
| `LLM_MODEL` | имя модели |
| `TARGET_NETWORK` | соцсеть, под которую оформляет паблишер: `VK` или `Telegram` |

Шаблон — в `.env.example`.

## Вывод

Вся переписка агентов идёт в стандартный вывод.

## Трассировка

Прогон отправляется в Langfuse, если заданы все три переменные `LANGFUSE_*`

## Структура

```
main.py              точка входа: настройки из окружения → сборка → запуск
app/
  config.py          настройки (единственное место, где читается окружение)
  brief.py           чтение файла с брифом
  personas.py        системные промпты ролей и правила соцсетей
  llm/factory.py     создание клиента чат-модели
  agents/
    base.py          AgentSpec + LLMAgent: одна механика узла для всех ролей
    catalog.py       состав команды и параметры каждой роли
  graph/
    state.py         состояние графа и счётчики запусков
    routing.py       разбор вердикта редактора и развилка графа
    builder.py       сборка графа из готовых узлов
  langfuse.py        подключение Langfuse: клиент и колбэк-хендлер или (None, None)
  runner.py          ContentFactory: настройки → модель → агенты → граф → прогон
  reporting.py       форматирование результата
briefs/              брифы
```
## Результаты прогонов

Для реализации задачи использовались две модели: **yandex-gpt** и **deepseek-v4-flash**.

### yandex-gpt

Работала с более коротким latency, но с более низкой производительностью при
генерации контента: для получения минимального удовлетворительного результата
требуется большее количество циклов и сессий. После 6–7 сессий и оценки качества
сгенерированного контента пригодными для дальнейшего использования оказались не
более 1/5 постов. Примерно половина запусков завершились результатом 0/5 пригодных
постов по оценке постановщика задачи. Таким образом, модель для этой задачи не
подошла, и было решено заменить её на другую.

### deepseek-v4-flash

Справилась с поставленной задачей лучше: из 8 сессий одна дала результат 5/5
(с минимальными возможными доработками), одна — 0/5, остальные — 3/5, но требовали
существенных доработок. В одном случае модель выдумывала и искажала факты.

### Наблюдения

1. В целом копирайтер удерживает контекст. Из восьми сессий в одной копирайтер
   на втором круге справился с задачей генерации первого поста, но при других
   настройках `temperature` и `effort`, учёт которых не вёлся, поэтому предыдущие настройки не
   сохранены. Остальные сессии запускались в один цикл для каждого агента.
2. Качество критики редактора в большинстве случаев обоснованное (см. приложение).
3. В случаях, когда редактор отправлял пост копирайтеру на доработку, замечания
   (несоблюдение формата, добавить интриги, переформулировать CTA) были обоснованы
   (с некоторым допущением) с точки зрения задачи и были корректно восприняты
   копирайтером, после чего в следующем цикле вносились структурные изменения в
   текст и усиление эмоциональной нагрузки (см. приложение).
4. С задачей SMM для производителя вапр-двигателей справился хорошо, несмотря на
   абсурдность задачи.
